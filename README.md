# Marketplace

Домашнее задание: OpenAPI, CRUD товаров и заказы. Python 3.12, FastAPI, PostgreSQL 17, SQLAlchemy 2 и Flyway.

## Запуск

Нужны Docker с Compose 2.24+ и Python 3 для создания `.env` и запуска демонстрации.

```bash
make setup
make up
docker compose logs -f api
```

API: http://localhost:8000. Swagger UI: http://localhost:8000/docs. Контракт: http://localhost:8000/openapi.json.

`make setup` создаёт локальные пароли и ключ JWT. Повторный запуск не меняет существующий `.env`. Файл исключён из Git. PostgreSQL доступен только внутри сети Compose, API слушает localhost.

При запуске Compose сначала ждёт PostgreSQL, затем выполняет миграции Flyway и только после успешной миграции запускает API. Данные остаются в Docker volume после `make down`.

## Демонстрация

```bash
make demo
docker compose exec db psql -U marketplace -d marketplace
```

Сценарий регистрирует продавца и покупателя, создаёт товар и промокод, оформляет заказ, уменьшает количество позиций ниже порога промокода и отменяет заказ. Затем проверяет повторную отмену и некорректный товар. Пароли и токены в вывод не попадают. В конце печатаются SELECT-запросы с ID созданных записей.

```sql
SELECT id, name, price, stock, status, seller_id FROM products;
SELECT id, user_id, status, total_amount, discount_amount, promo_code_id FROM orders;
SELECT order_id, product_id, quantity, price_at_order FROM order_items;
SELECT code, current_uses, max_uses FROM promo_codes;
SELECT user_id, operation_type, created_at FROM user_operations ORDER BY created_at;
SELECT version, description, success FROM flyway_schema_history;
```

Чтобы проверить ADMIN:

```bash
make admin
```

Команда спросит логин и пароль. Затем можно войти через `POST /auth/login` в Swagger UI. В кнопку **Authorize** нужно вставить только `access_token`. Регистрация через API создаёт USER или SELLER, но не ADMIN.

## Генерация из контракта

Источник API — `openapi/marketplace.yaml`. Модели создаёт `datamodel-code-generator`, а `scripts/generate.py` генерирует маршруты FastAPI по `operationId`, параметрам, схемам и `x-roles`. Маршруты вызывают одноимённые функции из `app/operations.py`. Ручных DTO и ручных CRUD-маршрутов нет.

В Docker генерация выполняется при сборке. Для локальной генерации:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
make generate
```

Результат находится в `app/generated/` и исключён из Git. Скрипт сначала проверяет сам OpenAPI, затем создаёт модели и маршруты. Для изменения поля нужно менять контракт и повторять генерацию.

## Основные решения

Деньги считаются через `Decimal` с округлением `ROUND_HALF_UP` до копеек. В БД используется `NUMERIC(12,2)`, в JSON — число. В контракте стоят `format: decimal` и `multipleOf: 0.01`. Сумма, которая не помещается в `NUMERIC(12,2)`, отклоняется до записи.

Товары удаляются переводом в ARCHIVED. GET возвращает товары любого статуса; убрать архивные можно фильтром. Пагинация начинается с нуля, размер по умолчанию 20, максимум 100. Фильтры применяются вместе, категория сравнивается точно.

Создание, обновление и отмена заказа выполняются внутри `Session.begin()`. Исключение откатывает остатки, позиции, промокод и запись операции. HTTP-ответ возвращается после фиксации транзакции.

Строка пользователя блокируется через `SELECT FOR UPDATE`, чтобы параллельные запросы не обходили лимит частоты и проверку активного заказа. Дополнительно есть частичный уникальный индекс: не более одного CREATED или PAYMENT_PENDING на пользователя.

Товары блокируются в порядке UUID, затем блокируется промокод. Такой порядок используется при создании, обновлении и отмене: конкурирующие запросы не могут продать один остаток дважды или превысить `max_uses`. Проверки остатков возвращают список всех позиций, которых не хватает.

При обновлении доступный остаток считается как текущий свободный остаток плюс предыдущий резерв этого заказа. Затем резервируется новый набор. Это эквивалентно возврату старого резерва и новому резервированию внутри одной транзакции. Повторяющиеся `product_id` запрещены до входа в бизнес-логику.

Цена сохраняется в `price_at_order`. Существующая позиция при обновлении заказа сохраняет свою цену; впервые добавленная получает текущую. Изменение каталога не меняет уже сохранённые цены.

При обновлении промокод проверяется заново. Уже занятое данным заказом использование не считается новым: `max_uses=1` не мешает обновлять единственный заказ с этим промокодом. Если сумма стала ниже порога, промокод снимается и `current_uses` уменьшается. Истёкший или отключённый промокод возвращает `PROMO_CODE_INVALID`; обновление откатывается. При отмене использование возвращается даже у уже истёкшего промокода.

Фразу условия «но не более 70% ... в ином случае цена 100%» трактую буквально: процент выше 70 означает нулевую скидку. Фиксированная скидка ограничена суммой заказа. Эти случаи вынесены в тесты.

Статусы идут по цепочке CREATED → PAYMENT_PENDING → PAID → SHIPPED → COMPLETED. Отмена доступна из CREATED и PAYMENT_PENDING через отдельный endpoint. Для демонстрации переходов добавлен `POST /orders/{id}/status`, доступный ADMIN. Обновление позиций допускается только в CREATED. Повторная отмена возвращает 409 и не возвращает остатки повторно.

Лимит создания и обновления независимый. `ORDER_INTERVAL_MINUTES` задаёт интервал, по умолчанию одна минута. Считаются только успешные операции. При работе ADMIN с чужим заказом лимит относится к ADMIN, который отправляет запрос.

JWT содержит `sub`, `role`, `type`, `jti`, `iat`, `exp`, `iss`, `aud`. Access живёт 20 минут, refresh — 14 дней. Refresh хранится в БД по идентификатору `jti`, сам токен не сохраняется. При обновлении старая запись отзывается под блокировкой и выдаётся новая пара. Пароли хешируются Argon2id.

Валидация выполняется до бизнес-операций: сгенерированные модели проверяют типы и ограничения, дополнительная проверка исходного JSON запрещает неявное преобразование строки в число и учитывает `nullable`, `multipleOf` и `additionalProperties`. Ошибки содержат `details.fields`. Роли проверяются в dependency, права на конкретный товар или заказ — внутри транзакции.

Каждый HTTP-запрос получает новый UUID. Логи содержат method, endpoint, status_code, duration_ms, user_id, timestamp, request_id. Для POST, PUT и DELETE добавляется тело запроса, пароли и токены заменяются на `***`. Некорректный JSON и слишком длинные тела не записываются целиком.

## Проверки

```bash
make test
```

Проверки используют отдельный Compose-проект `marketplace-tests` и БД `marketplace_test`. Обычная БД приложения не затрагивается. Перед каждым тестом очищаются только таблицы тестовой БД. Каждый ответ проверяется на соответствие исходному OpenAPI, а изменения остатков, заказов и промокодов — через SELECT.

Проверяются CRUD, мягкое удаление, фильтры, границы входных полей, ошибки, роли и чужие объекты, снапшоты цен, откат транзакций, лимиты операций, состояния заказа, скидки, JWT, ротация refresh и маскирование логов. Отдельные параллельные тесты проверяют остаток, активный заказ, лимит промокода и повторную отмену.

Остановка тестовой БД без удаления данных:

```bash
docker compose -p marketplace-tests -f compose.yaml -f compose.test.yaml down
```

## Что показать на защите

1. `make up` и логи запуска API/Flyway.
2. `make demo`, затем SELECT в PostgreSQL.
3. Неактивный товар, недостаточный остаток, чужой заказ и повторную отмену.
4. Тесты и исходный контракт рядом со сгенерированными моделями и маршрутами.
5. `create_order`, `update_order`, `cancel_order`, блокировки и обработчик ошибок.

Почему нужен `FOR UPDATE`: обычный SELECT не мешает двум транзакциям прочитать один и тот же остаток. Блокировка заставляет второй запрос дождаться результата первого и проверить уже обновлённые данные.

Почему не `float`: двоичная арифметика не представляет все десятичные дроби точно. `Decimal` и `NUMERIC` позволяют явно задать точность денег и правило округления.

Чем аутентификация отличается от авторизации: первая устанавливает пользователя по токену, вторая проверяет роль и право на конкретный объект.

Зачем нужны миграции: схема имеет версии и контрольные суммы. Flyway применяет только новые миграции и фиксирует их в `flyway_schema_history`.

Почему недостаточно проверки активного заказа в Python: два конкурентных запроса могли бы пройти её одновременно. Поэтому есть блокировка пользователя и уникальный индекс в PostgreSQL.
